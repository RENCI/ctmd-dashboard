How to reproduce this investigation

All queries below run against the production database via a port-forward. You need the cluster kubeconfig and the ks alias (or plain kubectl).

shell open a tunnel to ctmd-db2
export KUBECONFIG=~/.kube/sterling
ks port-forward svc/ctmd-db2 -n ctmd 5439:5432   # leave running
shell connect with psql (credentials are in the db-dsn-pipeline2 secret)
psql "postgresql://ctmd-user:<password>@localhost:5439/postgres"
NoteThe DB password is intentionally omitted here — pull it from the Kubernetes secret db-dsn-pipeline2 (ks get secret db-dsn-pipeline2 -n ctmd). The API and pipeline2 both read this same database.

Data model — what’s available to filter & chart

The CTMD database has 40+ tables, all keyed by ProposalID. Below is the landscape, then the field-level schema for the tables these change requests touch. Fields highlighted filter are the ones directly useful for the requested filters/charts.

Read this first — the name lookup table Most coded columns (status, TIC assignment, funding source, phase, …) store an integer index, not text. The human-readable label lives in the name table, joined on (table, column, index) → description. Every filter that shows a label does this join. Its columns are: table, column, index, id, description (752 rows).

Finding 1 — “TIN Cycle” is derived, not stored

Several requests filter or compare by TIN Cycle 1.0 vs 2.0. There is no cycle column anywhere in the schema. It has to be derived from the TIC assignment. Here is the query that lists the assignable institutions:

sql TIC/RIC institutions in the name lookup
SELECT "index", description FROM "name"
WHERE "column" = 'assignToInstitution' ORDER BY "index";

Result → mapped to the cycles named in the change-request doc

sql proposals per assignment (the counts above)
SELECT n.description AS tic, count(*)
FROM "AssignProposal" ap
JOIN "name" n ON n.index = ap."assignToInstitution"
                AND n."column" = 'assignToInstitution'
GROUP BY n.description ORDER BY count(*) DESC;
ConclusionThe cycle→TIC mapping must live in one authoritative place (a DB lookup is preferred so it changes without a deploy). Open question: where do VUMC RIC and NCATS sit — their own bucket, or excluded from cycle comparisons?

Finding 2 — Proposal statuses & category presets

The requests ask for status checkboxes and presets (“Initial Consults”, “Comprehensive Consults”, “Pilots”, “Full Implementation Studies”, “Resources”). The data has 33 distinct statuses; the categorization logic already exists in the app (in two places that disagree — see §Code).

sql distinct statuses with counts
SELECT n.description AS status, count(*)
FROM "Proposal" p
JOIN "name" n ON n.index = p."proposalStatus"
                AND n."column" = 'proposalStatus'
GROUP BY n.description ORDER BY n.description;

Finding 3 — Milestone date fields & their coverage

Timeline Metrics and per-proposal timelines depend on milestone dates. They exist across several tables, but coverage drops sharply for grant/funding stages — the charts must handle small-N gracefully.
